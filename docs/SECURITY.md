# Security design and hardening checklist

This document describes what the system protects, how, and what you must still do
yourself. It is a working checklist — not a security certification.

---

## 1. Security boundary (read this first)

- The system handles **virtual credits only**. There is no payment integration,
  no cash-in/cash-out, no e-wallet, no card data, and nothing of monetary value
  to steal at the application layer.
- It is designed for a **private LAN**, not the public internet.
- The largest real risks are therefore: **insider manipulation of records**,
  **credential sharing between tellers**, **device/session misuse**, and
  **data loss** — which is exactly what the controls below target.

---

## 2. Controls implemented in the code

### Authentication

| Control | Where |
|---|---|
| Passwords hashed with bcrypt | `User` cast `'password' => 'hashed'` |
| Generic failure message (no user enumeration) | `AuthController::login` |
| Login throttling: 5 failures per username+IP, 300 s lockout, plus a 20/min route throttle | `RateLimiter` + `throttle:20,1` |
| Session ID regenerated on login (fixation defence) | `$request->session()->regenerate()` |
| Session invalidated + CSRF token rotated on logout | `AuthController::logout` |
| Account status enforced on every request | `EnsureRole` middleware |
| Every sign-in, failure and block recorded | `login_events` table |

### Authorisation

- Three roles: `supervisor`, `game_master`, `teller`; route groups protected by
  the `role:` middleware.
- **Object-level checks** in controllers: a Game Master can only touch their own
  events, fights, tellers and bets (`abort_unless(... game_master_id === ...)`).
- A teller only ever queries rows filtered by their own `teller_id`.
- The Supervisor is intentionally **read-only on transactional records** — they
  can allocate virtual credits and manage accounts, but cannot declare results,
  edit bets, or rewrite history.
- UI hiding is never the only control; every rule is enforced server-side.

### Request and transport hardening

`SecurityHeaders` middleware sets on every response:

```
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; frame-ancestors 'self'; ...
X-Content-Type-Options: nosniff
X-Frame-Options: SAMEORIGIN
Referrer-Policy: same-origin
Permissions-Policy: geolocation=(), microphone=(), camera=()
```

- No CDN, no inline scripts, no third-party JS — the UI ships its own CSS/JS, so
  the policy can stay strict and the system works offline.
- All state-changing requests are `POST`/`PATCH` with Laravel CSRF tokens.
- Blade escapes output by default (no raw `{!! !!}` in any view).
- All database access is parameterised through Eloquent/query builder.

### Terminal (POS) binding

- Each browser gets a random fingerprint in `localStorage`.
- A workstation row stores the approved fingerprint; `POS_STRICT_DEVICE_BINDING=true`
  refuses a teller login when the fingerprint or the assigned terminal does not match.
- Revoking a workstation clears its fingerprint immediately.

### Financial-record integrity

- **Append-only ledger.** Every credit movement is a new `wallet_transactions`
  row; balances are never edited by controllers, only by `WalletService` inside a
  DB transaction with a row lock.
- Each ledger row stores `balance_after`, so any wallet can be re-derived and
  compared: `php artisan system:verify`.
- Bets are append-only except for status transitions; voids require a reason and
  an actor and produce a refund row.
- Fight transitions use compare-and-swap SQL (`WHERE status = ...`), so two Game
  Masters cannot double-settle a fight.
- **Hash-chained report snapshots**: each snapshot stores `payload_hash` and the
  previous snapshot's hash. Editing a sealed report breaks the chain and
  `system:verify` reports it.
- **Audit log** records actor, role, action, entity, before/after values, IP and
  workstation for every administrative and betting action.

### Data minimisation

- No player identities, no government IDs, no payment details, no biometrics.
- Login events store IP and a truncated user agent only.

## 3. Hardening checklist — you must do these

### Before first real use

- [ ] Change **every** seeded password (supervisor, both GMs, all tellers).
- [ ] Create real accounts per person; delete or suspend the demo ones.
- [ ] `.env`: `APP_ENV=production`, `APP_DEBUG=false`, `APP_URL` set to the real URL.
- [ ] `php artisan config:cache` and `php artisan route:cache` after final changes.
- [ ] Set `POS_STRICT_DEVICE_BINDING=true` and bind each POS terminal.
- [ ] Set a strong `APP_KEY` (already generated by install; never share it).
- [ ] Serve over **HTTPS** (`docs/NETWORK-SETUP.md`) and install the CA on terminals.

### Database

- [ ] Do **not** use MySQL `root` for the application. Create a dedicated user:

```sql
CREATE DATABASE esabong CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'esabong_app'@'localhost' IDENTIFIED BY 'a-long-random-password';
GRANT SELECT, INSERT, UPDATE, DELETE ON esabong.* TO 'esabong_app'@'localhost';
FLUSH PRIVILEGES;
```

- [ ] Remove `DROP`/`ALTER` grants from the app user; run migrations as an admin user.
- [ ] Bind MySQL to `127.0.0.1` only (`bind-address=127.0.0.1` in `my.ini`).
- [ ] **Do not expose phpMyAdmin on the LAN.** If you need it, restrict it to the
      server's own browser (`Require local`) or disable it.
- [ ] Back up nightly and store a weekly copy off the machine.

### Server OS

- [ ] Dedicated Windows user for the server service, no browsing/email on it.
- [ ] Windows Update enabled; antivirus exclusion for `mysql-data` (prevents locks).
- [ ] BitLocker (or at least a BIOS password + locked case) so a stolen SSD does
      not hand over the database.
- [ ] Physical control: the server and switch in a locked cabinet; only the
      Supervisor has console access.
- [ ] Disable RDP unless required; if used, restrict to LAN + strong password + MFA.
- [ ] Remove or disable XAMPP's default `dashboard`, `webalizer`, `phpMyAdmin`
      virtual hosts if they are not needed.

### Operational discipline

- [ ] One account per person, never shared. Discipline a teller by **suspending**
      their account (audited) rather than letting them use someone else's login.
- [ ] Tellers close their shift at the end of every session; unclosed shifts are
      visible on the Game Master monitor.
- [ ] Supervisor reviews the audit log weekly (failed logins, voids, credit grants).
- [ ] Voids and credit allocations always carry a reason.
- [ ] Keep the sealed report snapshots — they are the record of what was reported
      at the time.

## 4. Threat → control summary

| Threat | Control |
|---|---|
| Teller edits another teller's bets | Object-level scoping to the authenticated teller |
| Game Master settles a rival's fight | Ownership check on event → game master |
| Supervisor rewrites a past report | Append-only snapshots + hash chain + verify command |
| Double-click double-charges a wallet | Row-locked transaction + duplicate window + idempotency keys |
| Bet accepted after the fight starts | Status compare-and-swap inside the bet transaction |
| Shared login from a home PC | Terminal binding + strict mode |
| Brute-force password guessing | Rate limiter + lockout + audit |
| Session hijack | Regenerated session IDs, HttpOnly cookies, HTTPS |
| SQL injection / XSS | Parameterised queries, Blade escaping, strict CSP |
| Silent record tampering | Audit log with before/after + append-only ledger |
| Power loss during a bet | InnoDB `flush_log_at_trx_commit=1`, transactional writes |
| Data loss / disk failure | Nightly dumps + off-machine weekly copy + restore drills |

---

## 5. What this system does NOT protect against

- A **server administrator** with database access. Anyone who can run SQL can
  alter data; the hash chain and audit log make it *detectable*, not impossible.
  Restrict DB access to one trusted person and review the chain regularly.
- A compromised POS PC with a keylogger.
- Malicious collusion between a Game Master and a teller (detectable through the
  audit trail and odds/void patterns, not preventable by software).
- Regulatory compliance. Records, retention and reporting obligations for
  gambling operations are a legal matter — consult counsel before operating
  anything connected to real wagering, and note the current national suspension
  of e-sabong operations in the Philippines.

---

## 6. Incident response (quick)

1. **Suspected credential leak:** suspend the account (audited), reset the
   password, review `login_events` and `audit_logs` for that user.
2. **Ledger mismatch:** run `php artisan system:verify`, then reconcile the
   affected wallet from `wallet_transactions` (read `docs/OPERATIONS.md`) —
   never "fix" a balance with a raw UPDATE.
3. **Stolen terminal:** revoke its workstation fingerprint, close its shift,
   suspend the teller.
4. **Disk failure:** restore the latest dump to a new SSD, run
   `php artisan migrate` (no `--seed`), then `system:verify`.
